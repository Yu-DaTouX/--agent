# 方案 · 把「自动压缩」收进上下文工具（待审阅）

> 状态：**待你确认**，尚未动代码。相关参考：你给的 ChatGPT 对话《上下文梯度大小规律》里的
> Coding Context Manager 设计（工作集预算 / 四层压缩 / 归档可回溯）。
> 现有实现位置：`src/renderer/src/components/toolbar/RightPanel.tsx`（`ContextSection`）。

## 1. 问题（用截图说明）

右栏现在长这样：

```
┌ 上下文 ──────────────────────────┐
│ 上下文  9%              36k / 400k│   ← 主值是物理窗口占用
│ ▬▬▬▬▬▬▬▬▬▬▭────────────────────── │   ← 一条触发线记号
│ > 详情                           │   ← 折叠
│ 自动压缩        [开关]  [压缩上下文]│   ← 独立一行
└──────────────────────────────────┘
```

四条问题：

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **看起来像另一个工具**（你的原话） | 自动压缩被「详情」折叠区隔在主值之外，独立成行；它和「上下文」之间没有任何视觉隶属关系 |
| 2 | **主值语义会误导** | 显示的是**物理窗口**占用（`36k / 400k`）。换到 1M 模型时用户会以为"还早"，但编码模式真正该守的是**远低于物理窗口的工作集上限**（参考实践：1M → 约 240k） |
| 3 | **详情里混了三类东西** | ① 策略参数（阈值/保留最近/预留输出）② 能力开关（自动压缩开/关）③ 花销（本轮 $）。三者关注点不同，挤在一个折叠区 |
| 4 | **表达不了"会发生什么"** | 只能表达 pi 原生的单点阈值（`used > window - reserve` 就 compact）。没有阶段概念、没有"历史去哪了"、没有可回溯入口 |

## 2. 目标

让「上下文」这一个分区一屏回答三个问题：

1. 我离"该清理"还有多远？（**工作集**视角，不是物理窗口）
2. 下一步会自动发生什么？
3. 被清理的历史去哪了、能不能取回？

原则：**压缩是上下文的一种行为，不是一个并列的工具。**

## 3. 目标信息架构

主态（未过线）：

```
┌ 上下文 ───────────────────────────── 36k / 240k ─┐
│ 15%    ╷70%        ╷85%              ╷100%        │   ← 三个阶段记号
│ ▬▬▭────────────────────────────────────────────── │
│ 下一步：清理旧工具输出（约 168k 时）                │   ← 一行"下一阶段"
│                                                  │
│ 自动压缩  [开关]                        立即压缩   │   ← 归位：上下文主体内
│                                                  │
│ 详情 ⌄                                           │
│   物理窗口     1M                                 │
│   工作集上限   240k  （= min(窗口 × 70%, 240k)）   │
│   保留最近     32k                                │
│   预留输出     32k                                │
│   已归档       12 段 · 可回溯                      │
│   本轮花费     $0.32                              │
└──────────────────────────────────────────────────┘
```

过线态：把「下一步」换成警告色的「已达清理线，正在清理工具输出…」；压缩中：同位置显示进度文案（现有的 `status.compacting` 并入这一行，不再单独占一行）。

关键变化：

| 变化 | 前 | 后 |
|---|---|---|
| 主值 | `上下文 9%` + 物理窗口 | 工作集占用（`15%`）+ `36k / 240k` |
| 进度条记号 | 1 条（原生阈值） | 3 条（清理工具输出 / 折叠已完成 / 结构化压缩）——阶段 2 起才真实存在，阶段 1 先只画原生的那一条并标注 |
| 自动压缩 | 在「详情」下方独立一行 | 归入上下文主体，紧跟进度条 |
| 详情内容 | 参数 + 开关状态 + 花销 混排 | 分三组：容量参数 / 归档状态 / 花销 |
| 文案域 | 散在 `ctx.*`、`status.*`、`rp.*` | 全部收敛到 `ctx.*`，图标统一用 `layers` |

## 4. 分期落地（建议）

| 阶段 | 内容 | 成本 | 是否改策略 |
|---|---|---|---|
| **1. 归位** | 重排顺序（主值 → 进度条 → 自动压缩 → 详情）、详情分组、文案与图标统一、主值改工作集语义 | 1–2 h | 不改，纯 UI |
| **2. 过程可见** | 在 pi 的 `session_before_compact` 拦截点显示"正在做什么"；压缩完成后显示"已归档 N 段" | 半天 + 需扩展 | 不改压缩算法，只上报 |
| **3. 策略可控** | 砚侧托管：关掉 pi 原生 auto-compaction，由桌面端按工作集预算触发 RPC `compact(customInstructions)`，保留 90% 物理窗口的紧急兜底；设置里暴露参数（默认取参考值：窗口 70% / 上限 240k / 保留 32k / 预留 32k） | 1–2 天 + 真实模型验证 | **改策略** |
| **4. 可回溯** | 归档索引（`ctx://episode/N`、`ctx://tool/N`）+ `context_recall` 工具，让模型按引用取回原始内容 | 2–3 天 | 需要新工具与真实验证 |

阶段 2–4 依赖参考对话里的策略设计，且都要真实模型验证（烧额度）；**阶段 1 可以立刻做，不动任何行为**。

## 5. 明确不改的东西

- 不引入第二条滚动条（右栏只有一个滚动容器）。
- 不恢复"显示还差多少 token"的数字行 —— 你此前明确要求"在进度条上有记号即可"（见 `RightPanel.tsx` 内注释）。本方案的「下一步」一行是**阶段名**而非倒计时数字，若你仍不想看到，可以只保留 hover/title。
- 阶段 1 不触碰 pi 的压缩行为，压缩仍然由 pi 自己触发。

## 6. 需要你拍板

1. **主值语义**：改成"工作集占用"（推荐，物理窗口下沉到详情），还是保持"物理窗口占用"？
2. **「下一步」提示行**：是否允许这一行存在？（它与早期"不要显示还差多少"的要求相邻，需要你确认边界）
3. **阶段 2–4 是否现在排期**：涉及扩展点、策略接管与真实模型验证成本，建议阶段 1 先落地、看到效果再决定。
